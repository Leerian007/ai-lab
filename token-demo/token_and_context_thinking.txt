前端会把之前的对话全部放在一个类似上下文集合里面，这个集合结构类似这样有List<Map<String,String>>
[
    {
        "msg": "我是一个大三的计算机大学生，你推荐我学什么语言",
        "role": "user"
    },
    {
        "msg": "我不直接推荐“只学某一门语言”，而是根据你的基础和目标，分层给你建议",
        "role": "ai"
    }
]
两个标签msg标签表示输入与输出的文本也就是上下文，role标签表示角色，一般是两个角色，一个是user，一个是ai，user的msg是用户输入的内容，ai的msg是ai返回输出的内容。
    在每次提问的时候这个集合跟着当前的问题一起去请求后端。这个集合会随着时间越来越大，ai会忘记最前面的内容（这是最粗略的设计，类似于滑动窗口，这个窗口一直往后，如果内容
超出，那么最前面窗口无法覆盖的内容就会丢失，这个窗口就是上下文大小），这就是上下文丢失，AI 会彻底忘记你们一开始聊了什么，也就是俗称的“失忆”也可以通过后端写代码进行
summary提炼，让ai总结历史对话，再将简化总结的历史对话作为上下文随着当前的对话传给ai。但是目前最主流的还是rag，将历史对话塞入一个向量数据库，每次对话先根据当前的对话去数据库中搜索历史相关的内容，再将这几条最相关的几条历史对话发送给ai，不想一开始把所有的历史对话集合发给ai，这样就会节省很多token。
    但是历史对话被存入向量数据库的时候会经过类似于切分token的语义切割器进行切分，这个时候存入数据库的是一个个向量块，我们怎么将他们又重新组回原始的对话呢？目前有几种方法：Overlap 重叠切分、父级索引 Parent Document Retrieval、（保留元数据）Metadata,这里讲讲父级索引和元数据Metadata.
    父级索引是目前高级 RAG 框架（如 LangChain）最爱用的策略。它采用了“小块检索，大块返回”的思路。在数据库里存两份数据。一份是切得很碎的“子块”（用于精准匹配和检索），另一份是包含这些子块的完整“父块”（比如完整的 10 轮对话）。当 AI 通过“子块”找到相关线索后，代码不会只把子块喂给 AI，而是直接把整个“父块”拿出来喂给 AI。这样既保证了检索的精准，又保证了 AI 看到的是完整的上下文。
    元数据Metadata：对话和普通的长篇大论（如 PDF 文档）不同，对话是有严格结构的。在把对话存入向量数据库时，我们会给每一块打上标签（Metadata）。比如标记上 user_id: zhao、time: 2026-07-28、session_id: 12345。
检索时，代码不仅做“语义相似度搜索”，还会加一个“过滤条件”。比如：只检索 session_id = 12345 且时间最近的对话块。这样即使切碎了，捞出来的也一定是连贯的对话记录。
