1）一句话定义
vLLM 是用于高吞吐大语言模型推理的开源引擎；KV Cache 则是推理时缓存历史 Token 的 Key、Value 中间结果，以减少重复计算的一种机制。
2）核心机制
先理解大模型生成文本时的计算方式。
假设模型正在生成：
车辆可能存在点火系统……

当它要继续生成下一个 Token 时，通常需要利用前面已经生成的全部上下文。
如果每生成一个 Token 都从头重复计算之前所有 Token 的注意力相关结果，计算会产生大量浪费。
KV Cache 就是为了减少这部分重复计算。
在 Transformer 的注意力机制中，每个 Token 会产生 Key 和 Value 等中间表示。模型在生成后续 Token 时，可以复用历史 Token 对应的 Key、Value，而不必重新计算它们。
```
没有 KV Cache
生成第 4 个 Token 时，再计算前面 3 个 Token 的相关中间结果；生成第 5 个 Token 时，又重复计算更多历史内容。

使用 KV Cache
缓存之前的 Key、Value，生成新 Token 时只需计算新 Token 对应的部分，并复用历史结果。
```
可以将它理解为程序里的缓存：能复用的计算结果就不再重复执行。
但是，KV Cache 本身也需要占用显存。上下文越长、并发请求越多，缓存占用通常越大。

kv cache我的理解是把token的关联关系存储起来，用来复用，让大模型减少重复计算

理解得基本对，但更精确一点：它缓存的不是“token 的关联关系”，而是每个历史 token 已经算好的 Key 向量和 Value 向量。大模型生成文本是自回归的：每生成一个新 token，都要看前面所有 token。
如果没有 KV Cache，生成第 51 个 token 时，模型会把第 1–50 个 token 重新算一遍；生成第 52 个时，又把第 1–51 个重算一遍。这些历史 token 的 K、V 其实完全没变，重复计算非常浪费。

KV Cache 的做法是：
```
Prefill 阶段：
一次性把 prompt 里所有 token 的 K、V 算出来，写进显存

Decode 阶段：
每生成一个新 token，只算这个新 token 的 Q、K、V
历史 token 的 K、V 直接从缓存里读
把新 token 的 K、V 追加到缓存末尾
```

所以它不是把“关联关系”存起来，而是把已经投影好的 K、V 向量存起来，避免每步重新做线性变换。
为什么只缓存 K 和 V
因为 Attention 计算里，生成新 token 时只需要：
当前新 token 的 Query
所有历史 token 的 Key 和 Value
历史 token 的 K、V 一旦算好就不会变，所以值得缓存；而 Query 每一步都只用于当前 token，不具备跨步复用价值，所以通常不缓存。
代价是什么
KV Cache 是典型的用显存换速度。
上下文越长、并发请求越多，KV Cache 占用的显存就越大。长文本场景下，它甚至可能比模型权重本身还占显存。
所以后面才会出现 vLLM 的 PagedAttention、GQA、KV Cache 量化这些技术，目的都是降低 KV Cache 的显存占用，让同一张卡能同时服务更多请求。

KV Cache 缓存的是历史 token 的 K、V 向量，不是抽象的“关联关系”；它让模型在生成新 token 时不必重算前面所有 token，从而把重复计算省掉，代价是显存占用会随上下文长度线性增长。
