# RAG 核心机制：父级索引与上下文管理

## 1. 上下文传输的基础结构

前端通常会将历史对话封装为 `List<Map<String, String>>` 结构，每次请求时随当前问题一同发送给后端：

```json
[
    {
        "msg": "我是一个大三的计算机大学生，你推荐我学什么语言",
        "role": "user"
    },
    {
        "msg": "我不直接推荐"只学某一门语言"，而是根据你的基础和目标，分层给你建议",
        "role": "ai"
    }
]
```

## 2. 上下文丢失与解决方案演进

前端会把之前的对话全部放在一个类似上下文集合里面，这个集合结构类似这样 `List<Map<String, String>>`：

```json
[
    {
        "msg": "我是一个大三的计算机大学生，你推荐我学什么语言",
        "role": "user"
    },
    {
        "msg": "我不直接推荐"只学某一门语言"，而是根据你的基础和目标，分层给你建议",
        "role": "ai"
    }
]
```

两个标签 `msg` 标签表示输入与输出的文本也就是上下文，`role` 标签表示角色，一般是两个角色，一个是 `user`，一个是 `ai`，`user` 的 `msg` 是用户输入的内容，`ai` 的 `msg` 是 AI 返回输出的内容。

在每次提问的时候这个集合跟着当前的问题一起去请求后端。这个集合会随着时间越来越大，AI 会忘记最前面的内容（这是最粗略的设计，类似于滑动窗口，这个窗口一直往后，如果内容超出，那么最前面窗口无法覆盖的内容就会丢失，这个窗口就是上下文大小），这就是上下文丢失，AI 会彻底忘记你们一开始聊了什么，也就是俗称的"失忆"。

也可以通过后端写代码进行 summary 提炼，让 AI 总结历史对话，再将简化总结的历史对话作为上下文随着当前的对话传给 AI。

但是目前最主流的还是 RAG，将历史对话塞入一个向量数据库，每次对话先根据当前的对话去数据库中搜索历史相关的内容，再将这几条最相关的几条历史对话发送给 AI，不想一开始把所有的历史对话集合发给 AI，这样就会节省很多 token。
### 2.1
如果模型支持100万token为什么还需要rag？
首先是成本问题，如果每次请求都花费海量token，那么费用就会非常贵。其次是Attention和Lost in the Middle（中间遗忘）问题。
假设一句话： 小明昨天买了一辆特斯拉，今天他开着它去了公司。 模型在预测"公司"的时候，并不是从左往右读，而是会计算每个 Token 和其他 Token 的关系。
```plain
它  ---> 特斯拉（权重很高）
它  ---> 小明（有一定权重）
它  ---> 昨天（权重很低）
```
这就是 Attention。 理论上，每个 Token 都可以关注所有 Token，所以很多人就会得出一个结论："那只要 Context 足够大，不就什么都能记住了吗？"实际上不是。
假设你的上下文有 100 万个 Token。 模型不会把这 100 万个 Token 当成一样重要。 它会给每个 Token 一个 Attention Score（注意力权重）。
也就是说，很多 Token 虽然在上下文里，但几乎没有参与最终推理。 所以它们不是"丢失"了，而是影响力非常小。
```plain
Token A：0.35
Token B：0.28
Token C：0.15
……
Token 999999：0.00001
```
为什么会出现 Lost in the Middle（中间遗忘） 这是一个很经典的实验。 假设有一个很长的 Prompt：
```plain
前面：
今天北京天气很好……

中间：
密码是 123456……

后面：
请告诉我密码是多少。
```
很多模型都会出现一个现象： 如果密码放在开头，回答正确率很高。 如果密码放在最后，回答正确率也很高。 如果密码放在正中间，正确率明显下降。
这就是 Lost in the Middle。 为什么？
目前没有一个唯一的解释，但普遍认为有几个原因： 
开头通常包含 System Prompt 和任务描述，本身权重就比较高。 最后面的内容距离当前生成位置最近，对预测影响最大。 中间的信息数量最多，容易被大量无关 Token "稀释"。
所以，并不是模型看不到中间，而是中间的信息竞争不过前后的信息。

为什么 Context 越长，不代表效果越好？
这就像你考试的时候，老师把整个图书馆搬到你桌子上，然后问你一道题。 你当然能找到答案，但速度会很慢，而且容易被大量无关内容干扰。 
如果我先帮你找到维修手册中关于 P0010 的两页，再交给你，你回答反而更准确。 这其实就是 RAG 的思想。

所以，RAG 真正解决的是什么？
很多教程都会说： RAG 是解决 Context Window 不够的问题。 我觉得这句话已经有点过时了。 更准确的说法应该是： RAG 是一个信息检索系统，它负责把"海量信息"压缩成"当前问题最需要的信息"，然后交给 LLM 推理。
也就是说，RAG 的重点不是扩展上下文，而是提高上下文的信息密度（Information Density）。

我想再补充一个容易忽略的观点,你有没有发现，RAG 本质上其实不像 AI，而更像搜索引擎？ 实际上，很多 AI 应用架构师都认为： RAG = Information Retrieval（信息检索）+ LLM（语言推理）
其中：
Embedding、向量数据库、余弦相似度，这些都是搜索技术。
LLM 才负责理解和生成。 所以一个 RAG 系统的效果，很大程度上不是由 GPT 决定的，而是由检索质量决定的。
## 3. 切块后的上下文重组难题

但是历史对话被存入向量数据库的时候会经过类似于切分 token 的语义切割器进行切分，这个时候存入数据库的是一个个向量块，我们怎么将他们又重新组回原始的对话呢？目前有几种方法：

- Overlap 重叠切分
- 父级索引 Parent Document Retrieval
- 保留元数据 Metadata

这里讲讲父级索引和元数据 Metadata。

## 4. 核心方案详解

### 4.1 父级索引 (Parent Document Retrieval)

父级索引是目前高级 RAG 框架（如 LangChain）最爱用的策略。它采用了"小块检索，大块返回"的思路。

- **存储策略**：在数据库里存两份数据。
    1. **子块**：切得很碎的"子块"（用于精准匹配和检索）。
    2. **父块**：包含这些子块的完整"父块"（比如完整的 10 轮对话）。
- **检索逻辑**：当 AI 通过"子块"找到相关线索后，代码不会只把子块喂给 AI，而是直接把整个"父块"拿出来喂给 AI。
- **效果**：这样既保证了检索的精准，又保证了 AI 看到的是完整的上下文。

### 4.2 元数据过滤 (Metadata)

元数据 Metadata：对话和普通的长篇大论（如 PDF 文档）不同，对话是有严格结构的。

- **存储策略**：在把对话存入向量数据库时，我们会给每一块打上标签（Metadata）。比如标记上 `user_id: zhao`、`time: 2026-07-28`、`session_id: 12345`。
- **检索逻辑**：检索时，代码不仅做"语义相似度搜索"，还会加一个"过滤条件"。比如：只检索 `session_id = 12345` 且时间最近的对话块。
- **效果**：这样即使切碎了，捞出来的也一定是连贯的对话记录。
